<task type="auto">
  <name>Task 1: Implement authentication middleware and rate limiting</name>
  <files>src/middleware/auth.ts, src/middleware/rate-limit.ts</files>
  <action>
    1. Create `src/middleware/auth.ts`:
       - authenticate: Express middleware that:
         - Extracts Bearer token from Authorization header
         - Verifies JWT using jsonwebtoken with JWT_SECRET
         - Attaches decoded user to req.user
         - Returns 401 if token missing/invalid/expired
         - Handles token refresh automatically if using express-jwt with autoRefresh

       - optionalAuth: Same as authenticate but calls next() even if no token

    2. Create `src/middleware/rate-limit.ts` using express-rate-limit:
       - apiLimiter: General API limiting - 100 requests per 15 minutes per IP
       - authLimiter: Auth endpoints - 20 requests per 15 minutes per IP
       - smsLimiter: SMS sending - 10 requests per hour per phone number
       - Set standardHeaders: true, legacyHeaders: false

    Apply authLimiter to /api/auth/* routes in the main Express app.
  </action>
  <verify>
    <automated>curl -X GET http://localhost:60000/api/user/profile</automated>
    Expected: 401 Unauthorized (no token)
    <automated>curl -X GET http://localhost:60000/api/user/profile -H "Authorization: Bearer invalid"</automated>
    Expected: 401 Unauthorized
  </verify>
  <done>
    - Middleware protects authenticated routes
    - Valid JWT token grants access
    - Invalid/missing token returns 401
    - Rate limiters configured and applied
    - Rate limit headers present in responses
  </done>
</task>

<task type="auto">
  <name>Task 2: Implement token refresh and logout</name>
  <files>src/routes/auth/refresh.post.ts, src/routes/auth/logout.post.ts</files>
  <action>
    1. Create `src/routes/auth/refresh.post.ts` with POST /api/auth/refresh:
       - Accept {refreshToken}
       - Verify the refresh token JWT (check signature, expiry)
       - Extract user ID from token
       - Look up hashed refresh token in database
       - Compare provided token hash with stored hash
       - Check token not expired
       - Generate new access token (15min) and refresh token (7day)
       - Revoke old refresh token (delete from DB)
       - Store new refresh token hash
       - Return {accessToken, refreshToken}
       - Handle errors: 401 for invalid/expired/revoked token

    2. Create `src/routes/auth/logout.post.ts` with POST /api/auth/logout:
       - Accept {refreshToken} (optional - can logout without it)
       - If refreshToken provided:
         - Hash the token
         - Delete from refresh_tokens table
       - Optionally add to blacklist in Redis (if available)
       - Return 200 OK

    Both endpoints should create audit log entries.
  </action>
  <verify>
    <automated>curl -X POST http://localhost:60000/api/auth/refresh -H "Content-Type: application/json" -d '{"refreshToken":"eyJ..."}'</automated>
    Expected: 200 with new accessToken and refreshToken
  </verify>
  <done>
    - Valid refresh token returns new token pair
    - Expired refresh token returns 401
    - Used refresh token returns 401 (token revoked after use)
    - Logout invalidates the refresh token
    - Audit logs created for refresh and logout actions
  </done>
</task>

<task type="auto">
  <name>Task 3: Implement password reset flow</name>
  <files>src/routes/auth/forgot-password.post.ts, src/routes/auth/reset-password.post.ts, src/services/sms.ts</files>
  <action>
    1. Create `src/services/sms.ts`:
       - sendSmsCode(phone, purpose): generates 6-digit code, stores in sms_codes table with expiry (5 min), sends via SMS provider
       - verifySmsCode(phone, code, purpose): validates code exists, matches, not used, not expired, marks as used
       - For development: if SMS provider not configured, log code to console
       - Rate limit: same phone can only request code once per minute

    2. Create `src/routes/auth/forgot-password.post.ts` with POST /api/auth/forgot-password:
       - Accept {email?} or {phone?}
       - Find user by email or phone
       - If user found:
         - Generate 6-digit reset code
         - Store in sms_codes with purpose='reset_password', expiry 30 minutes
         - Send via SMS (for phone) or store for email (email sending deferred to Phase 3)
         - Return 200 (always return success to prevent enumeration)
       - If user not found: still return 200 (security best practice)
       - Create audit log

    3. Create `src/routes/auth/reset-password.post.ts` with POST /api/auth/reset-password:
       - Accept {email, code, newPassword} or {phone, code, newPassword}
       - Verify the reset code using verifySmsCode
       - Validate newPassword using passwordSchema
       - Hash new password
       - Update user's password_hash
       - Reset failed_login_attempts to 0
       - Clear locked_until
       - Revoke all existing refresh tokens (force re-login)
       - Return 200 OK
       - Create audit log for PASSWORD_RESET

    Use the existing passwordSchema from Plan 01.
  </action>
  <verify>
    <automated>curl -X POST http://localhost:60000/api/auth/forgot-password -H "Content-Type: application/json" -d '{"email":"test@example.com"}'</automated>
    Expected: 200 OK
  </verify>
  <done>
    - Password reset request returns 200 regardless of user existence
    - Reset code stored with correct expiry (30 minutes)
    - Valid reset code allows password change
    - New password must meet strength requirements
    - Password reset revokes all existing sessions
    - SMS codes expire after 5 minutes
    - Used SMS codes cannot be reused
  </done>
</task>
